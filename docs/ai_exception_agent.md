# AI Exception Resolution Agent

> **Accounting should be deterministic. AI should be assistive.**

`src/ar_reconciliation/agent/` analyses the bank receipts that the deterministic
reconciliation engine could not resolve. It classifies the exception, explains the
root cause, and recommends a specific next action for a human to approve.

---

## 1. Where it sits in the pipeline

```
scripts/run_reconciliation.py
        │
        ├── Reconciled Open AR
        ├── Processed Bank Receipts
        ├── Unmatched Bank Receipts   ◄── 64 receipts in the sample data
        ├── Data Quality Checks
        └── Summary
                │
                ▼
scripts/run_agent.py
        │
        ├── AI Exception Review   ◄── one row per unmatched receipt
        └── AI Exception Log      ◄── every validation repair and error
                │
                ▼
        Human review (Approval = APPROVE)
                │
                ▼
scripts/run_agent.py --apply-approved
        │
        └── AR updated, control totals re-verified
```

The agent runs **after** the engine and **never before** it. It cannot influence
a single match the engine made.

---

## 2. Design rules

1. **The agent never decides.** It produces a recommendation, a confidence level
   and a proposed invoice set. A human decides.
2. **The agent never applies anything on its own.** Applying requires
   `--apply-approved` and an explicit `Approval = APPROVE` in the review sheet.
3. **The agent never mutates source data.** `Bank_Cash_Receipts.xlsx` and
   `Open_AR_Detail.xlsx` are opened read-only.
4. **The agent never posts to a general ledger.** It *proposes* a journal entry
   in the `Proposed GL Posting` column. No ERP integration exists.
5. **The model is never trusted.** Every answer passes through a validator that
   repairs or downgrades it. See section 6.
6. **The engine's decisions are not overturned.** A scenario the engine marked
   review-only can never be auto-matched, no matter what the model says.

---

## 3. Running it

### Offline, deterministic (default)

```bash
python scripts/run_agent.py
```

No API key, no network access. The `rules` backend applies a transparent
heuristic and always produces the same answer for the same input.

### LLM backend

```bash
export OPENAI_API_KEY=sk-...
python scripts/run_agent.py --backend llm --model gpt-4o
```

Any OpenAI-compatible endpoint works:

```bash
python scripts/run_agent.py --backend llm \
    --base-url http://localhost:11434/v1 \
    --model llama3.1 \
    --api-key ollama
```

| Option | Default | Meaning |
|---|---|---|
| `--result` | `Open_AR_Detail_Reconciled_Result.xlsx` | Workbook to analyse |
| `--backend` | `rules` | `rules` (offline) or `llm` |
| `--model` | `gpt-4o` | Model identifier |
| `--base-url` | `OPENAI_BASE_URL` | Custom API base URL |
| `--api-key` | `OPENAI_API_KEY` | API key |
| `--apply-approved` | off | Apply the approved recommendations to AR |

Environment variables `OPENAI_API_KEY`, `OPENAI_BASE_URL` and `AR_AGENT_MODEL`
are also honoured.

### Applying approvals

```bash
python scripts/run_agent.py --apply-approved
```

## 4. The review sheet

`AI Exception Review` is written into the result workbook. One row per unmatched
receipt.

| Column | Meaning |
|---|---|
| `Bank Transaction ID` | The receipt being reviewed |
| `AI Exception Type` | One of 20 controlled exception types (section 5) |
| `Root Cause` | Why the receipt did not match, in one or two sentences |
| `Recommended Action` | One of 5 controlled actions (section 5) |
| `AI Confidence` | `High`, `Medium` or `Low` |
| `Proposed Invoice Numbers` | The invoices the agent believes the cash belongs to |
| `Proposed Applied Amount` | How much to apply |
| `Proposed Residual Amount` | What stays open on the invoice afterwards |
| `Candidate Invoices Considered` | The pool the agent was allowed to choose from |
| `Accounting Treatment` | How the accounting should be handled |
| `Proposed GL Posting` | The journal entry that would be proposed |
| `AI Explanation` | The narrative addressed to the AR analyst |
| `Analysed By` | Which backend produced the answer |
| `Approval` | **The human's decision.** `APPROVE` or `REJECT` |
| `Reviewer Notes` | Free text for the reviewer |
| `Applied To AR` | Whether the recommendation was applied |

### The approval ledger

`AI_Exception_Approvals.xlsx` holds the same sheet as a durable record. The
result workbook is regenerated by `src/ar_reconciliation/services/reconciliation.py` on every run, so without
the ledger the reviewer's decisions would be lost.

The workbook wins over the ledger when both hold a decision for the same
receipt, so an edit made directly in Excel is never overwritten by a stale
ledger entry.

An approval is carried over **only while the proposal is unchanged**. If the
recommendation moves to a different invoice or a different amount, the stale
approval is dropped and the row returns to the queue for review.

## 5. Controlled vocabularies

### Exception types

`Short Payment`, `Overpayment`, `Partial Payment`, `Duplicate Payment`,
`Bank Fee`, `FX Difference`, `Missing Customer`, `Wrong Legal Entity`,
`Credit Memo`, `Refund`, `Chargeback`, `On-Account / Unapplied`,
`Ambiguous Invoice Reference`, `Dispute Payment`, `Tax Withholding`,
`Future-Dated Receipt`, `Unexpected Bank Account`, `Collector Hold`,
`Data Quality Issue`, `Unknown`.

A type outside this list is mapped to `Unknown` and logged.

### Recommended actions

| Action | Meaning |
|---|---|
| `Auto Match` | Safe to apply once a human approves |
| `Recommend Match` | A specific invoice should be applied by a human with customer context |
| `Manual Review` | Insufficient evidence, a person must investigate |
| `Hold / Escalate` | Needs an accounting treatment decision |
| `Return to Customer` | The payer must be asked for more information |

### Confidence

| Level | Meaning |
|---|---|
| `High` | The evidence unambiguously identifies one invoice and the amount is exact |
| `Medium` | One invoice is clearly the most likely, but a human must confirm the intent |
| `Low` | The evidence does not distinguish between candidates |

Only `High` may carry an `Auto Match`, and even then only after a human approves.

---

## 6. The validator

The validator is the control that makes it safe to let a language model touch
reconciliation output. It runs on both backends.

| Rule | Effect |
|---|---|
| Exception type outside the taxonomy | Mapped to `Unknown`, logged |
| Confidence outside the three levels | Downgraded to `Low`, logged |
| Action outside the five actions | Downgraded to `Manual Review`, logged |
| Proposed invoice not in the candidate pool | Discarded, logged |
| Proposed amount negative | Reset to 0, logged |
| Receipt carries no positive net amount | Amount discarded, action forced to `Hold / Escalate` |
| Proposed amount above the cash received | Capped to the cash received, logged |
| Proposed amount above the combined open amount | Capped, logged |
| Amount proposed with no invoice named | Amount discarded, logged |
| Proposed residual disagrees with the AR data | Recomputed from the AR data, logged |
| `Auto Match` with `Medium` or `Low` confidence | Downgraded to `Recommend Match`, logged |
| `Auto Match` / `Recommend Match` with no invoice | Downgraded to `Manual Review`, logged |
| `Low` confidence with an automatic action | Downgraded to `Manual Review`, logged |
| Scenario is review-only in the engine | `Auto Match` downgraded to `Recommend Match`, logged |
| Scenario needs a treatment decision | Forced to `Hold / Escalate`, logged |
| Residual too large for an automatic match | `Auto Match` downgraded to `Recommend Match`, logged |

Every repair is written to the `AI Exception Log` sheet with the receipt ID and the
reason.

## 7. The candidate pool

The agent may only consider an invoice that is:

- in the **same currency** as the receipt, and
- in the **same customer**, resolved by ERP Customer ID, or — when the bank feed
  carries no ERP Customer ID — by a customer name that resolves to exactly one
  ERP customer.

The amount used for ranking is the **remaining balance** (original open amount
minus what has already been applied), so an invoice that was partly settled by an
earlier receipt can still take the cash.

Invoices that the deterministic engine already cleared in full are excluded.

At most 12 candidates are ranked and shown to the model. The ranking is a
transparent heuristic: an invoice named in the memo scores highest, an exact
amount match scores highly, a small residual scores moderately, and a disputed
invoice is penalised.

### Ambiguity is never resolved by guessing

If two candidate invoices have the same residual — which is a real business case,
because customers genuinely have invoices with identical amounts — the tie is
treated as ambiguity. The recommendation drops to `Manual Review` rather than
picking one.

## 8. The rules backend

The offline backend mirrors the LLM prompt's policy exactly:

1. A receipt with no positive net amount proposes nothing.
2. A candidate with an exact amount match is proposed only when no rival
   candidate is equally close.
3. A candidate within 10% of the receipt amount is proposed only when it is the
   unique plausible candidate.
4. The memo scenario then overrides the action:
   - review-only scenarios are capped at `Recommend Match`,
   - scenarios needing an accounting decision (`Collector Hold`,
     `Reversal / Chargeback`, `Refund`, `Credit Memo`, `On-account / Unapplied`,
     `Lockbox Batch`) are forced to `Hold / Escalate`.

On the sample data it produces 4 `Recommend Match`, 18 `Hold / Escalate`,
2 `Return to Customer` and 40 `Manual Review` out of 64 unmatched receipts.

## 9. The LLM backend

The model receives a system prompt that fixes the rules (never invent an invoice,
never apply more than the cash received, defer rather than guess) and a user
prompt containing the receipt and its ranked candidates.

The response must be a single JSON object with a fixed schema:

```json
{
  "exception_type": "Short Payment",
  "root_cause": "The payer withheld a freight claim deduction of $250.",
  "recommended_action": "Recommend Match",
  "confidence": "Medium",
  "proposed_invoices": ["INV-900175"],
  "proposed_amount": 8123.75,
  "proposed_residual": 251.25,
  "accounting_treatment": "Apply the cash and raise a deduction case.",
  "gl_posting": "Dr Bank 8,123.75 / Cr AR - INV-900175 8,123.75.",
  "explanation": "The memo states a freight claim deduction..."
}
```

### Structured output negotiation

The backend probes the endpoint once at startup to find out whether it honours a
`json_schema` response format.

- **If it does**, the schema is enforced by the decoder's grammar. The model
  physically cannot emit a value outside the controlled vocabulary, or a key that
  is not in the schema. This is what makes a small local model reliable.
- **If it does not**, the backend falls back to `{"type": "json_object"}`, which
  at least guarantees a parsable JSON object, and relies on the validator.

See [Free and Open-Source Model Backends](local_models.md) for the measured
behaviour on a local model.

### Parallelism

`--concurrency N` analyses N receipts at a time. The requests are I/O bound while
the model generates, so a small thread pool cuts the wall clock sharply on a
local model. Each receipt is still a separate call, so the reasoning for every
receipt stays individually auditable.

### Failure handling

If the call fails, the agent logs the error and falls back to the rules backend
for that receipt, so one bad response cannot stop the run. Every fallback is
recorded in the `AI Exception Log` sheet.

## 10. Write-back safety

`--apply-approved` applies only rows whose `Approval` cell is `APPROVE`.

| Guard | Behaviour |
|---|---|
| Receipt already applied | Skipped, logged |
| Invoice already fully settled | Rejected, logged |
| Invoice not found in AR | Rejected, logged |
| Invoice has no open amount left | Rejected, logged |
| Approved amount above the open amount | Capped, logged as `Adjusted` |
| Applied amount above the cash received | Capped at the open amount |

After the write-back the control totals are recomputed:

```
AR applied amount total   ==   Bank applied amount total
```

If they do not balance, **the workbook is not written** and the run exits with a
non-zero status.

The write-back is idempotent. Re-running `--apply-approved` applies nothing the
second time.

## 11. Testing

```bash
python test_llm_backend.py
```

This spins up a local HTTP server that mimics an OpenAI-compatible endpoint, so
the LLM code path — request construction, JSON parsing, validation — is
exercised with no network access and no API key.

The canned model answer deliberately contains an invoice outside the candidate
pool, an amount far above the cash received, a residual that disagrees with the
AR data, and an `Auto Match` on a review-only scenario. The test asserts that all
four are caught and repaired.
